# Каталог документации в формате neurodoc

Формат называется neurodoc.
Формат neurodoc представляет собой набор текстовых файлов.
Внутри каждого файла находится блок знаний или информации.
Все файлы в кодировке UTF-8.

Начинать читать надо с корневого файла - он всегда называется root.
Остальные файлы находятся в папке _content.
Их имена являются уникальными идентификаторами в рамках данного каталога.
Идентификаторы - это UUID в нижнем регистре.

В тексте любого файла может встретиться ссылка вида [текст](uuid). Например, вот так: [подход к разработке](5c673c53-8ad9-49eb-9fb6-ffb3954848f0).
Это значит, что это ссылка на другой файл в папке _content с именем 5c673c53-8ad9-49eb-9fb6-ffb3954848f0, а "подход к разработке" - её текст (якорь), встроенный в предложение.
Текст ссылки может быть пустым: [](5c673c53-8ad9-49eb-9fb6-ffb3954848f0). Тогда вместо него показывают заголовок целевого файла - его первую непустую строку.
Текст ссылки не содержит символа "]" и переводов строк.

UUID сам по себе ссылкой не считается. UUID, обрамлённый символами "<" и ">", - это ссылка старого формата, она больше ссылкой не считается.

Кроме папки _content в каталоге могут быть папки с файлами в собственных форматах (YAML, SVG, конфиги). Имена у них не UUID, а доменные: эти файлы читают не только люди, но и программы.
В ссылке вместо UUID может стоять путь к такому файлу - относительно того файла, в котором написана ссылка. Например, ссылка [auth.start](../contract/auth/start.yaml), написанная в файле из папки _content, ведёт на файл contract/auth/start.yaml этого же каталога.
Ссылка по пути ведёт только внутрь каталога neurodoc. За пределы каталога ссылок нет.

Таким образом, файлы образуют граф знаний, который имеет в качестве корня знания из файла root.
Для быстрой обработки каталога neurodoc рекомендуется построить в памяти hash-таблицу (mapping) "имя файла" -> "контент".

## Этот каталог

Здесь описан Fikus — выдуманный сервис ухода за комнатными растениями. Проект придуман
целиком, чтобы показать формат на живом материале: все домены — в зарезервированной зоне
.example, адреса серверов — из диапазонов для документации.

Папок с файлами в собственных форматах здесь две.

contract — формальная часть контракта API: по одному YAML-файлу на операцию
(contract/<домен>/<операция>.yaml), общие DTO в contract/dto, шаблоны новых операций
в contract/_template. В каждом файле есть golden-фикстуры — канонический JSON, которым тесты
сервера и клиентов сверяют байты на проводе. Поэтому менять эти файлы надо вместе с кодом,
который их читает.

design — логотип (design/logo.svg) и дизайн-токены (design/tokens.json): цвета, отступы,
радиусы и шрифты. Их читает сборка веб-клиентов и мобильного приложения.

Файлы в собственных форматах — только цели ссылок. Запись вида [текст](что-то) внутри
YAML, SVG или JSON ссылкой не считается: источники ссылок — только root и файлы из _content.
Поэтому и ссылки-примеры в этом описании никуда не ведут.

## Что здесь посмотреть

Каталог собран так, чтобы в нём встретилось всё, что умеет формат:

- ссылки по UUID с якорем, встроенным в предложение, и ссылки с пустым якорем в списках
  «См. также» — вместо них показывают заголовок целевого файла;
- ссылки-пути на файлы в собственных форматах: из root — `contract/auth/start.yaml`, из файлов
  _content — `../contract/dto/Plant.yaml`;
- файлы _content в разных форматах: простой текст, Markdown, BPMN-схемы в SVG, конфиги nginx
  и systemd, скрипт bash, HTML-страница, JSON и AsciiDoc;
- ссылки внутри таких файлов спрятаны в комментарии (`# …` в конфигах и скрипте,
  `<!-- … -->` в HTML и SVG) или в строки массива `"$links"` в JSON — файл остаётся
  правильным для своей программы;
- веб-адреса — голые и в квадратных скобках;
- граф глубиной в пять шагов от root, где у многих файлов несколько кратчайших путей;
- одна намеренно битая ссылка — на глоссарий для переводчиков, который ещё не написан;
- два файла без входящих ссылок — пустой файл и черновик.

## С чего начать

Откройте root. Под оглавлением там есть маршрут «С чего начать читать» из шести ссылок — от
порядка проектирования до журнала решений. Дальше удобно идти по разделам: технический
дизайн, инфраструктура и эксплуатация, функциональные домены, процесс разработки и реестр
контракта API.
