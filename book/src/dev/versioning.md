# Версии и выпуски

У трёх приложений один номер версии, и хранится он в одном месте — в git-теге вида `vX.Y.Z`
на коммите в ветке `main`. Сборки читают его сами через `git describe`; в файлах проекта и в
коде номера нет.

## Один источник

Каждая платформа собирается своим инструментом — MSBuild, Cargo, Gradle, — и у каждого есть
поле для версии. Три поля — три места, где номер легко забыть поменять, и тогда платформы
разъедутся; тег же один на всех. Поэтому номер не пишут ни в `NeurodocEditor.csproj`, ни в
`Cargo.toml` (поля `version` там нет намеренно), ни в `build.gradle.kts`, ни в коде.

## Как сборка узнаёт версию

Каждая сборка задаёт git два вопроса:

```bash
git describe --tags --abbrev=0 --match "v[0-9]*"        # ближайший тег: числовая часть
git describe --tags --dirty --always --match "v[0-9]*"  # строка для показа
```

| Платформа | Кто спрашивает | Что получает | Где видно |
|---|---|---|---|
| Windows | таргет `SetVersionFromGit` в `NeurodocEditor.csproj` | `InformationalVersion`, `AssemblyVersion`, `FileVersion` | строка заголовка окна, сразу после названия |
| Linux | скрипт `linux/build.rs` | константа `neurodoc_editor::VERSION` | строка заголовка окна, сразу после названия |
| Android | функция `git()` в `app/build.gradle.kts` | `versionName`, `versionCode` | внизу диалога настроек |

На Android версия не в верхней панели — там имя проекта; это сознательное исключение из
правила «интерфейс у всех версий одинаковый». Windows и Linux вдобавок печатают при сборке
строку «Версия сборки: …».

## Что показывает приложение

| Сборка | Версия |
|---|---|
| ровно с тега | `0.2.0` |
| три коммита после тега | `0.2.0-3-g1a2b3c4` |
| есть незакоммиченные правки | `0.2.0-3-g1a2b3c4-dirty` |
| тегов ещё нет | `0.0.0+g1a2b3c4` |
| собрано без git (архив без `.git`, git не в `PATH`) | `0.0.0-nogit` |

Суффикс `-dirty` значит, что при сборке в репозитории были незакоммиченные правки: по такой
сборке нельзя точно восстановить, из чего она получена. Его даёт правка любого отслеживаемого
файла, даже документации, но не новые файлы, ещё не добавленные в git. `0.0.0-nogit` —
намеренно заметный маркер: лучше явно неправильная версия, чем правдоподобная выдумка; сборка
без git при этом не падает.

## Числовая часть

Не все поля терпят буквы, поэтому числовая часть берётся только из тега:

- **Windows** — `AssemblyVersion` и `FileVersion`, они из четырёх чисел: `0.2.0` → `0.2.0.0`;
- **Android** — `versionCode = major * 10000 + minor * 100 + patch`: `0.2.0` → `200`, без тега
  `1`; промежуточные сборки получают код своего тега;
- **Linux** — `build.rs` вычисляет и её, но приложение показывает только строку.

`versionCode` не должен уменьшаться: APK с меньшим кодом поверх установленного не встанет.
Формула однозначна, пока minor и patch меньше 100: у `0.1.100` и `0.2.0` код одинаковый — `200`.

## Выпуск версии

```bash
./release.sh 0.3.0
```

На Windows — `release.bat 0.3.0`, двойник с теми же проверками и сообщениями. Скрипт
откажется работать и ничего не изменит, если:

- аргумент — не три числа через точку;
- текущая ветка — не `main`: иначе тег назвал бы версию, которой нет в выпущенной истории;
- рабочее дерево не чистое (`git status --porcelain` не пуст — считаются и неотслеживаемые
  файлы): иначе тег указал бы не на то, что будет собрано;
- тег `vX.Y.Z` уже есть: теги не переносят, берут номер выше.

Если всё в порядке, скрипт ставит на текущий коммит аннотированный тег
(`git tag -a vX.Y.Z -m vX.Y.Z`). Push он не делает — публикация остаётся явным действием, — а
печатает команду:

```bash
git push origin main --follow-tags
```

`--follow-tags` отправляет только аннотированные теги: лёгкий тег, поставленный руками
(`git tag v0.3.0`), сборки на вашей машине увидят, а на сервер он так не уйдёт. Ставьте теги
скриптом.

Затем приложения пересобирают — номер вшивается при сборке; скрипт напоминает команды
`./linux-deploy.sh`, `./android-build.sh` и `build-deploy.bat` (см. [Сборка](build.md)). Cargo
заметит новый тег сам: `build.rs` следит за `.git/HEAD`, `.git/index`, `.git/packed-refs`,
`.git/refs/tags` и `.git/refs/heads`.

Готовых бинарных выпусков пока нет: выпуск — это тег, а приложения собирают из исходников
скриптами репозитория.

## Тонкости реализации

- **Windows.** Версию по умолчанию (`1.0.0`, а от неё `AssemblyVersion` и `FileVersion`) SDK
  задаёт ещё при вычислении проекта, когда git не опрошен. Поэтому таргет считает в собственные
  свойства (`_AppVersionNumeric`, `_AppVersionDisplay`) и не полагается на
  `Condition="'$(VersionPrefix)' == ''"`: такой откат не сработал бы никогда. Таргет стоит перед
  `PrepareForBuild`, до генерации атрибутов сборки, а `IncludeSourceRevisionInInformationalVersion`
  выключен — иначе SDK дописал бы к строке `+<sha>`. Приложение не упаковано в MSIX,
  `Package.Current` ему недоступен, поэтому `AppVersion.Display` читает строку из атрибута сборки.
- **Android.** git вызывается через `providers.exec`, а не `ProcessBuilder`: только он совместим
  с configuration cache Gradle. `isIgnoreExitValue = true` — на репозитории без тегов `describe`
  завершается с ошибкой, а сборка падать не должна.
